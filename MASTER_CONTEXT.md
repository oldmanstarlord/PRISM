DESIGN RULES D1 CONFIG-DRIVEN: windows, lookbacks, thresholds, weights, decay half-lives, peer-group rules, event mappings, policy rules and explanation templates live in versioned model_config rows (JSON, checksummed, status draft/approved/retired). No magic numbers in code except defaults seeded by migration. Every run stores config_version + config_fingerprint. D2 COMPONENT REGISTRY: every risk component is a row in score_component_definition plus a Python class implementing the Component protocol. Scorer, confidence engine, API and frontend read the registry. Adding or reweighting a component needs NO change to scorer, API schema or frontend. The same pattern applies to explainers. D3 RESULT ENVELOPE (SRS section 10): every derived result carries subject, effective time, method and version, input fingerprint, lookback, units, component contributions, thresholds, data-sufficiency status, confidence, limitations, computed_at. D4 POINT-IN-TIME: external data stores event_time, published_at and ingested_at. After-close publications affect the next trading day. Never overwrite; supersede with a new version row. Computing for date t uses only rows with published_at/ingested_at <= t. D5 API-DRIVEN UI: the frontend renders breakdowns, explanations, limitations, data-age and method info from API payloads with generic shared components. No component or dimension names hard-coded in UI code. D6 IDEMPOTENT RUNS: input fingerprint + config fingerprint => identical outputs; a repeat run reuses the completed run and creates no new rows. D7 EVERY STEP SHIPS: (1) additive Alembic migration, (2) backend module with typed code and tests, (3) API endpoints with response models, (4) frontend page/components with tests where the step has UI, (5) seed/config entries, (6) docs: PROJECT_STATUS.md update and proposed decisions in docs/specs/PROPOSED_DECISIONS.md (never edit the SRS yourself). D8 EXPLANATIONS ARE EVIDENCE-BOUND: every explanation sentence is produced from a template filled only with evidence items read from stored data. Each sentence lists its evidence_ids. A sentence without evidence is dropped. No language model writes explanation text. D9 NO ADVICE, NO CAUSAL CLAIMS: describe risk, statistical relationships and possible transmission paths. Banned: buy/sell/hold recommendations, price targets, predictions of future prices, certainty words ("will", "guaranteed"). Correlation is "moves together with", never "because of". News effects are "possible effect". Every explanation carries limitations, data age and the disclaimer. D10 TESTS NEVER TOUCH PRODUCTION: DB-backed tests use a dedicated test database (PRISM_TEST_DATABASE_URL) and refuse to run against the production database. Pure logic tests need no database. CI runs a Postgres service container. D11 NO FIXTURE OR FALLBACK DATA IN PRODUCTION FLOWS: fixtures live only under tests/fixtures. A failed or missing source means no write and a clear error or logged skip. Missing data makes a component "missing" and lowers confidence. Every dataset has a row in the data_source registry (added in Step 11b).
